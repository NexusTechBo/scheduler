# Entity and relation design

## Base template

```java
@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
@EqualsAndHashCode(of = "id")       // NEVER @Data: toString/hashCode would walk lazy relations
@Entity
@Table(name = "items")              // plural snake_case
public class Item {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String code;

    @Column(nullable = false)
    private String name;

    @Column(length = 500)
    private String notes;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 50)
    @Builder.Default
    private ItemStatus status = ItemStatus.PENDING;

    @Column(nullable = false)
    @Builder.Default
    private boolean active = true;  // soft delete

    @Version
    private Long version;           // optimistic locking for concurrently edited entities

    @Column(nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @PrePersist
    private void prePersist() { this.createdAt = LocalDateTime.now(); }
}
```

Rules:
- `@Builder.Default` on every field with an initial value (otherwise the builder leaves it null/false).
- `@Column(nullable = false, unique = true, updatable = false)` mirrors the DB; the source of truth is the migration (`ddl-auto: none`).
- Enums always `EnumType.STRING` (+ `CHECK` in SQL). Presentation logic for the enum lives in the enum (`getDisplayName()` with a `switch`).
- Date types: `LocalDate`, `LocalTime`, `LocalDateTime`, `DayOfWeek` (as STRING). The time zone is handled by the app's `Clock`.
- camelCase columns in Java → snake_case in the DB automatically (Spring's default naming strategy).
- Small, pure domain logic may live in the entity:
  ```java
  public boolean blocks(LocalTime start, LocalTime end) {
      if (Boolean.TRUE.equals(isFullDayBlock)) return true;
      return startTime != null && endTime != null && start.isBefore(endTime) && end.isAfter(startTime);
  }
  ```
- Global entities with multi-tenancy: `@Table(name = "tenants", schema = "public")`; tenant entities without `schema`.

## Relations

### @ManyToOne (the most common; the side holding the FK)

```java
@ManyToOne(optional = false, fetch = FetchType.LAZY)   // optional=false → INNER JOIN and NOT NULL
@JoinColumn(name = "owner_id")
private User owner;

@ManyToOne(fetch = FetchType.LAZY)                     // optional (nullable)
@JoinColumn(name = "category_id")
private Category category;
```
**Always `LAZY`** (the JPA default for ToOne is EAGER). What to fetch is decided in the repository (`JOIN FETCH` / `@EntityGraph`).

### @OneToMany (only if you need to navigate from the parent)

Prefer not mapping it and querying by the child (`findByOwnerId`). If needed:
```java
@OneToMany(mappedBy = "owner", fetch = FetchType.LAZY)
@Builder.Default
private List<Booking> bookings = new ArrayList<>();
```
`cascade = CascadeType.ALL, orphanRemoval = true` only for real compositions (order lines), never towards independent entities.

### @ManyToMany with a join table and no extra data

Owning side (the one you modify):
```java
@ManyToMany(fetch = FetchType.LAZY)
@JoinTable(
    name = "user_project",
    joinColumns = @JoinColumn(name = "user_id"),
    inverseJoinColumns = @JoinColumn(name = "project_id"))
@Builder.Default
private List<Project> projects = new ArrayList<>();
```
Inverse side:
```java
@ManyToMany(mappedBy = "projects", fetch = FetchType.LAZY)
@Builder.Default
private List<User> members = new ArrayList<>();
```
Modify from the owner (`user.getProjects().add(project); repository.save(user);`), checking `contains` first to avoid duplicates. `contains`/`remove` work because `equals` is by `id`. Use a `Set` if order doesn't matter and the collection is large.

If the relation needs attributes (assignment date, role) → an explicit join entity with two `@ManyToOne`, not `@ManyToMany`.

### Roles in the same table

A user with role `MEMBER` can be the target of a `@ManyToOne owner` in other entities; validating that the referenced user has the right role belongs in the service (`findByIdAndRoleAndActiveIsTrue`).

## Equivalent Flyway migration

```sql
CREATE TABLE IF NOT EXISTS items (
    id BIGSERIAL PRIMARY KEY,                       -- or BIGINT GENERATED BY DEFAULT AS IDENTITY
    code VARCHAR(255) NOT NULL,
    name VARCHAR(255) NOT NULL,
    notes VARCHAR(500),
    owner_id BIGINT NOT NULL REFERENCES users(id),
    category_id BIGINT REFERENCES categories(id),
    status VARCHAR(50) NOT NULL DEFAULT 'PENDING'
        CHECK (status IN ('PENDING', 'CONFIRMED', 'CANCELLED')),
    active BOOLEAN NOT NULL DEFAULT TRUE,
    version BIGINT,
    created_at TIMESTAMP NOT NULL,
    CONSTRAINT uq_items_code UNIQUE (code)
);

-- Conditional uniqueness: one active slot per owner/time
CREATE UNIQUE INDEX IF NOT EXISTS uq_items_owner_start_active
    ON items (owner_id, start_time) WHERE status <> 'CANCELLED';

CREATE TABLE IF NOT EXISTS user_item (
    user_id BIGINT NOT NULL REFERENCES users(id),
    item_id BIGINT NOT NULL REFERENCES items(id),
    PRIMARY KEY (user_id, item_id)
);
```
Java ↔ SQL mapping: `Long`→`BIGINT`, `String`→`VARCHAR(255)` (or `length`), `boolean`→`BOOLEAN`, `LocalDateTime`→`TIMESTAMP`, `LocalTime`→`TIME WITHOUT TIME ZONE`, `LocalDate`→`DATE`, enum→`VARCHAR(50)` + `CHECK`.
Index FKs used in frequent filters (`CREATE INDEX ix_items_owner_id ON items(owner_id)`): PostgreSQL doesn't do it automatically.

## Anti-patterns

- `@Data` or `@ToString` without excluding relations → infinite recursion / accidental lazy loading.
- `FetchType.EAGER` on any relation.
- `@EqualsAndHashCode` over all fields (breaks `Set`/`contains` when data changes).
- Exposing the entity in the controller (use DTO + mapper).
- `CascadeType.REMOVE` towards shared entities; physical deletes where soft delete is expected.
- Uninitialized collections (`null`) → NPE on `add`; always `= new ArrayList<>()` + `@Builder.Default`.
